# 实施路线图

## 顺序与依赖

1. **Foundation**：项目骨架、配置、模型、错误体、健康检查、质量门禁。
2. **Protocol**：真实 proto 生成、Line/frame/Gzip parser、限制与契约 fixture。
3. **Security + Inbox**：凭据、scope、PostgreSQL/Alembic、事务幂等和整批 ACK。
4. **Raw evidence**：claim/lease、OTLP Logs、重试/dead letter、原始事件可恢复。
5. **Data truth**：V3 occurrence-bound event identity、首批字段注册表、installation HMAC、时间/质量/隐私/cardinality 契约。
6. **First vertical slice**：新版本 Java Crash/ANR 对比、指纹/详情、数据质量、告警触发/恢复。
7. **Operations**：指标、审计、retention、Docker、反向代理、备份/runbook。
8. **Performance scenarios**：启动/帧/网络，再逐步扩展资源、IO、SQLite、WebView、IPC。
9. **Symbolization/config**：制品、worker、签名配置和客户端 occurrence-bound build identity 联调。
10. **Production gate**：SigNoz staging、读取隔离、压测、soak、故障注入、安全、灾备、发布与回滚。

顺序上的关键变化是：不能从“OTLP Log 已可查”直接跳到大量 Dashboard。字段注册、身份分母和数据状态先完成，首个真实用户闭环验收后再扩展信号面。

## Git 交付策略

统一实现线为 `codex/server-foundation`，其中已包含原 `codex/collector-v2-e2e` 的 V2 Collector 联调提交；后者只保留为历史引用，不再作为独立工作目录。每个里程碑使用英文 `Type: Subject` commit（`Feat/Fix/Refactor/Perf/Style/Docs/Revert/Build`）。只有用户明确要求时才创建提交、推送或 Draft PR；PR 在 M1/M2 验收证据齐全前不得标记 ready。

## 第一轮开发工作包

以下工作包只覆盖首个真实用户闭环，不同时铺开所有采集模块。每个包都要保留原始事实并可独立回退；数据库变化使用新的 append-only migration。

### WP0：外部 staging 基线

- 准备 PostgreSQL 16、TLS ingress、独立 SigNoz/Foundry staging 和测试通知渠道。
- 回放当前真实 V2 uploader fixture，验证 commit 后 ACK、并发重复、代理丢响应、OTLP 可见和现有资产导入。
- 在真实 SigNoz 复核已修正的 exact `core/sdk_health`、`crash/java_crash`、`anr/anr_detected` 资产；保持 `production_ready=false` 且不接通知。

退出：Collector 的生产持久化边界和真实 SigNoz API 已现场验证；若外部环境尚不可用，后续包可开发但不能关闭生产门禁。

### WP1：发生时身份与 installation 假名化

- Android 客户端与服务端已冻结 schema V3：每条 durable event 保存 app version name、versionCode、appBuild、variant、installation；Native frame 可再保存 ABI/module build-id/name/module-relative PC/load bias。
- 服务端新增 decoder/契约 fixture，并持久化 `release_identity_quality`。已有 request/batch 元数据保留，但回填为 `REQUEST_DECLARED/BATCH_DECLARED`，不能冒充 occurrence 事实。
- append-only migration 增加 `installation_hmac`、`installation_hmac_key_version` 及必要质量列；Gateway 在写 inbox 前 HMAC 并移除明文。
- 冻结 key domain、保管、轮换/断点、删除和双 tenant 隔离规则。

本地状态：代码、migration、冲突/重放测试和真实 V2/V3 loopback 已完成；生产退出仍要求跨升级设备 fixture、PostgreSQL/TLS、密钥轮换和全输出明文扫描。

### WP2：字段注册与 normalization

- 以 `(schema,module,name,field)` 建立代码内版本化注册表，首批只覆盖 `java_crash`、`anr_detected`、`app_exit`、`core/sdk_health` 及其必要 identity/quality 字段。
- 固化 occurrence/collection/received time、raw/aggregated、availability、单位/类型、PII/cardinality、Log/Metric 投影。
- `app_exit` 发生时间取 `exitTimestamp`；普通退出、异常退出证据、现场 Crash/ANR 分开。未知字段仍在 raw，但 mapper 不再自动把所有 map 展平为属性。
- 派生结果带 `normalization_version`，映射失败只降级字段/投影，不丢 durable raw。

退出：固定 registry snapshot/漂移测试通过；高基数随机 corpus 不扩散到默认 OTLP attributes；所有数据状态可复核。

本地状态：首批 exact registry、normalization version、allow-listed OTLP attributes、事件指纹与数据状态已实现；全 SDK 事件目录、OTLP Metrics 和真实 cardinality 负载仍待扩展。

### WP3：首个查询与读取边界

- 实现四个逻辑查询契约：发布版本对比、Top fingerprints、单事故/事件详情、数据可信度。可先由 SigNoz 查询适配器提供，接口不能暴露 ClickHouse 内部表。
- 所有响应携带适用的 `state/value/numerator/denominator/sample_count/coverage/as_of/source`，tenant/app/environment 从认证 scope 强制注入。
- L0 聚合、L1 元数据、L2 raw 详情按 `docs/03-安全与租户.md` 分权；raw 查看/导出/break-glass 记录安全审计。
- 只计算事件数、受影响安装、活跃安装及门禁后的安装比率；session 指标返回明确 unavailable。

退出：两个 tenant 的正/负向读取测试、分页/窗口/查询预算和 raw 权限测试通过；真零、缺失、错误、迟到不会混淆。

本地状态：`apmq1` viewer/investigator、release-health/fingerprint/data-quality、事件分页/元数据/raw、HMAC cursor、人工发布决策已完成；同源 Web 现已消费这些接口，并用短时 HttpOnly session/CSRF 保留 Bearer 兼容。生产 SSO、RLS/限流与真实多租户部署仍待现场验收。

### WP4：Dashboard、告警与决策审计

- 发布健康页面使用 exact `crash/java_crash`、`anr/anr_detected`，并展示 identity、SDK drop、late 和样本门禁。
- 指纹详情并列 raw/symbolized evidence；`app_exit` 仅作为相关候选证据。
- 新建告警 fixture 验证低样本抑制、触发、分组、静默、通知重试、恢复；阈值在 staging 取得基线前保持 `TBD`。
- 记录发布负责人继续灰度/暂停/回滚的 actor、版本、证据窗口和理由，不让服务端自动替人做发布决定。

退出：真实 fixture 从 Dashboard 决策入口走到受限 raw 详情并返回，告警完整触发/恢复；旧模板不在生产路由。

本地状态：React/TypeScript/Vite 页面已覆盖筛选、质量、指标、指纹、事件/L2 raw 和人工决策；synthetic SQLite preview 与真实 Android debug ingest 入口已准备。退出条件仍被真实 PostgreSQL/TLS/SigNoz、告警通知、生产身份和浏览器现场验收阻塞。

### WP5：生产门禁与扩展

- 对首个切片执行 PostgreSQL/代理故障注入、容量、72h soak、备份恢复、安全和多租户隔离验收。
- 通过后才复用注册表与状态契约扩展启动/帧/网络；资源、IO、SQLite、WebView、IPC 依据真实 integration coverage 逐步加入。
- Native 精确符号化在 occurrence build/module identity、固定 R8/LLVM 镜像、对象存储/KMS 和真实每 ABI fixture 全部就绪后启用。

退出：`docs/07-测试与验收.md` 的相应 P0/P1 证据可复核，外部阻塞为零或显式接受延期，不用本地单测替代现场结论。

## 决策门

- **M1 前**：确认客户端 v1 header 的静态接入值和生产 key 发放方式。
- **M2 前**：准备可用 PostgreSQL 与 SigNoz staging OTLP endpoint；冻结单租户 staging 与共享多租户 Query/BFF/物理隔离边界。
- **首个切片查询实现前**：本地实现已冻结 tenant-scoped HMAC 与 occurrence 质量语义；生产前仍需确定 KMS/轮换 runbook、活跃安装窗口、最小样本和版本基线选择流程。
- **首个切片生产验收前**：客户端 V3 occurrence 已实现；仍须在真实跨升级设备、PostgreSQL/TLS/SigNoz staging 和通知链上验收。V2 batch resource 只用于兼容查询。
- **精确符号化前**：客户端补齐 occurrence-bound versionCode/appBuild/variant/ABI/module build-id/module-relative PC，部署固定工具，并完成生产凭据签发/轮换流程。
- **Session 指标前**：单独冻结 telemetry session 生命周期、ID、跨进程/重启和采样语义；不能用 installation 替代。
- **M4 前**：确定部署地区、域名/TLS、保留期、通知渠道、对象存储、RPO/RTO 和目标吞吐。

这些决策门不会阻止先完成可测试的服务端实现，但会阻止相应里程碑被标记为生产完成。
