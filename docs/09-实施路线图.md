# 实施路线图

## 顺序与依赖

1. **Foundation**：项目骨架、配置、模型、错误体、健康检查、质量门禁。
2. **Protocol**：真实 proto 生成、Line/frame/Gzip parser、限制与契约 fixture。
3. **Security + Inbox**：凭据、scope、PostgreSQL/Alembic、事务幂等和整批 ACK。
4. **Worker + OTLP**：claim/lease、mapper、重试/dead letter、SigNoz staging。
5. **Operations**：指标、审计、retention、Docker、反向代理、备份/runbook。
6. **Product assets**：Dashboard、告警、字段注册表、查询入口。
7. **Symbolization/config**：制品、worker、签名配置和客户端联调。
8. **Production gate**：压测、soak、故障注入、安全、灾备、发布与回滚。

## Git 交付策略

基础实现位于 `codex/server-foundation`，V2 Collector 联调分支为 `codex/collector-v2-e2e`。每个里程碑使用英文 `Type: Subject` commit（`Feat/Fix/Refactor/Perf/Style/Docs/Revert/Build`）。可运行版本推送后创建 Draft PR 到 `main`，在 M1/M2 验收证据齐全前保持 Draft。

## 决策门

- **M1 前**：确认客户端 v1 header 的静态接入值和生产 key 发放方式。
- **M2 前**：准备可用 PostgreSQL 与 SigNoz staging OTLP endpoint。
- **M3 前**：客户端补齐 build/session/installation/ABI/build-id 以及动态 AuthProvider/配置客户端。
- **M4 前**：确定部署地区、域名/TLS、保留期、通知渠道、对象存储、RPO/RTO 和目标吞吐。

这些决策门不会阻止先完成可测试的服务端实现，但会阻止相应里程碑被标记为生产完成。
