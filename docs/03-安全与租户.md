# 安全、隐私与租户模型

## 信任边界

APK 和网络请求均不可信。tenant 身份只能来自服务端验证过的凭据；`appId`、environment、版本、installationId 和事件 fields 都是需要校验的声明。SigNoz/ClickHouse 不直接暴露给移动端。

## 凭据模型

2026-09-07：Ingest/CI/Query 三类 key 的 Argon2 验证共用最多 2 个线程，无等待队列（默认 Argon2 每任务 64 MiB，最多约 128 MiB hashing 工作内存）。查询数据库前使用进程级 20 次/秒、突发 40 次的固定内存 token bucket；不基于未认证 key ID、IP 或 X-Forwarded-For 分配无界缓存。过载返回 retryable 429 + Retry-After: 1。请求取消仍持有并发槽，直到实际 hash 线程完成。未知 key 的 dummy verify 走同一执行器。此保护按进程计，入口对来源的公平配额和多副本全局限制仍属于反向代理/网关部署配置；Cookie 会话仍每次回查撤销状态。

- 初始接入使用随机 256-bit ingest key，显示一次；数据库只保存带版本的 Argon2id 哈希、key id、tenant、app/environment scope、状态和到期时间。
- 每次认证采用常量时间验证；缓存按短 TTL 保存解析后的 scope，不缓存原始密钥到日志或指标标签。
- 轮换允许新旧 key 短暂重叠，撤销立即使缓存失效并记录 actor/reason/request ID。
- 客户端已有每请求 `HttpHeaderProvider`；生产仍需建设短期 Token 签发/撤销/刷新服务并完成联调。长期管理凭据绝不进入 APK。
- 管理 API 与 ingest API 使用不同凭据、受众和网络入口。
- 构建流水线使用独立 `apmci1` key；数据库只存 Argon2id hash，scope 当前最小化为 `artifact:write`，可再绑定单一 app。ingest key、CI key 的版本前缀互不接受，制品凭据不能进入 APK。
- 查询使用独立一次性显示的 `apmq1` key，创建时固定 tenant/app/environment 和 `viewer` 或 `investigator` role。`viewer` 只能读取 L0 聚合；`investigator` 才能读取 L1/L2 和写入人工发布决策。三类 key 前缀互不接受。
- 浏览器只在 `POST /v1/web/session` 提交一次 `apmq1`，随后使用短时 host-only/HttpOnly/SameSite Cookie。签名 token 不含 raw key 或 tenant scope，每次请求按 key ID 回查撤销/到期；Cookie POST/DELETE 强制绑定 CSRF。生产要求 HTTPS Secure Cookie 和独立 session HMAC key。

## 租户隔离

- 所有业务表以 `tenant_id` 为第一隔离维度；查询 repository 强制注入 tenant context。
- 生产启用 PostgreSQL Row Level Security 作为纵深防御，并用跨租户负向测试验证。
- 唯一约束使用 `(tenant_id,event_id)`；凭据 scope 再限制 app/environment。
- SigNoz Community 自托管不能被假定提供本产品所需的强多租户 RBAC。第一阶段每个信任域/环境使用独立 SigNoz 实例或仅通过受控后端查询；不能把共享 SigNoz UI 直接开放给互不信任的客户。

## 数据最小化与 PII

- SDK 的 PII sanitizer 当前默认开启，`PRODUCTION_STRICT` 还会拒绝关闭脱敏；服务端仍做独立字段 allowlist/denylist、URL query、SQL literal、header、token、email/phone 等纵深清洗，不能把端上规则当唯一边界。
- `installationId` 使用受密钥保护、带 tenant/domain separation 的 HMAC 后再进入分析维度；不收集 Android advertising ID、IMEI、手机号等硬标识。
- 原始 payload 只在受控 inbox 保留，结构化日志不得打印它。
- 高风险字段被拒绝或置换时记录规则 ID 和计数，不记录原值。
- 提供 tenant/app/匿名主体维度的导出与删除任务，并覆盖 ClickHouse、PostgreSQL、对象存储和缓存。

### 当前 installation 实现

2026-09-07：清理覆盖包含已知 installation 的字符串、嵌套 map/list 和动态 key。归一化、Native identity、符号任务均从清理后的持久化证据生成；不完整 Native frame 被移除。必要事件/路由/发布身份若包含 installation，整批返回 `422 privacy_identity_conflict`，避免修改去重身份。正常旧批次重放继续按原 HMAC key version 校验；此前保留过污染字段的历史批次可能因更严格的规范化返回冲突，不能自动覆写已确认数据。此修复约束新接收数据，不声称已清理外部历史存储。

V2/V3 installation 假名化已按以下顺序落地：

1. 在认证 scope 和完整 envelope 校验通过后规范化 installation 字节；非法值整批拒绝。
2. 使用 secret manager/KMS 中的版本化密钥，对固定 domain、tenant ID 和 installation 值计算 HMAC-SHA-256；持久化 `installation_hmac` 与 `installation_hmac_key_version`。
3. 在写 durable inbox 前从规范化 payload 删除 installation 明文；请求原文不落盘，只保留安全请求哈希和计数审计。
4. OTLP、Query/BFF、Dashboard 和通知只接收 HMAC 或聚合值，不能接收明文或可逆映射。
5. 重放校验按已存在行保存的 key version 重新计算 HMAC，因此 active key 轮换不会把合法旧 batch 误判为冲突。生产仍必须规定旧版本保留窗口、泄漏处置和查询连续性；删除仍可能重放的旧 key 会 fail closed 并形成显式断点。

密钥由 `APM_INSTALLATION_HMAC_KEYS_JSON` 和 `APM_INSTALLATION_HMAC_ACTIVE_KEY_VERSION` 提供；每个 Base64 secret 至少 32 bytes，最多保留 16 个版本。空、弱、无 active version 的配置在遇到 installation-bearing batch 时返回可重试 `identity_service_unavailable`，不会回退保存明文。

HMAC 是可控的假名化标识，不等于匿名化：有密钥的一方仍可对候选值做验证，因此继续受访问、保留、导出和删除策略约束。legacy 或 installation 缺失事件保留 `IDENTITY_MISSING` 状态，只参与允许的事件计数，不进入安装分母。

### 字段分级与读取权限

| 数据级别 | 示例 | 默认可见范围 | 强制控制 |
| --- | --- | --- | --- |
| L0 聚合与注册维度 | exact event count、版本、环境、低基数状态、质量 coverage | tenant scoped viewer | Query/BFF 强制 tenant/app/environment、窗口和查询预算 |
| L1 事件元数据 | eventId、HMAC installation、scene/process、发生/接收时间、符号状态 | tenant investigator | 列表字段 allow-list、分页/导出限额、访问审计 |
| L2 原始诊断证据 | raw URL/SQL/path/stack/exception message/JS、任意 context/extras、ANR trace | 明确授权的 investigator，默认不进列表/通知 | 单事件/短窗口读取、purpose/reason、脱敏、审计、禁止缓存到共享前端 |
| L3 管理与制品 | mapping/ELF、密钥、配置发布、重放、删除/导出任务 | tenant admin、独立 CI 或平台受控角色 | 独立 credential/audience、双人或 break-glass 策略、完整审计 |

`viewer` 和 `investigator` 已在当前 fixed-scope Query/BFF 中实现：前者只能读取 L0 聚合，后者才可读取 L1/L2 并写入人工发布决策。`ci_artifact_writer` 当前由独立 `apmci1` + `artifact:write` scope 表达，还不是通用 RBAC 角色；`tenant_admin`、`platform_operator` 和跨租户 break-glass 仍是目标能力。平台运维身份默认只能看管线聚合健康，不能因为维护基础设施而自动获得所有 tenant 的 L2 原文；跨租户 break-glass 必须限时、说明原因并告警。

当前 raw 详情使用 `POST /v1/query/events/{event_id}/raw`：scope 只来自 `apmq1`，要求 investigator、固定 purpose code 和 10–512 字符 reason；审计事务 commit 后才返回 raw，并设置 `Cache-Control: no-store`。URL 以模板/host、SQL 以 fingerprint/table、path 以类别、异常/JS 以安全摘要进入常规 L0/L1；原文只在 L2 按需读取。共享 SigNoz UI 不能承担这条权限边界：多租户生产要么物理隔离 SigNoz，要么只通过受控 Query/BFF。

同源 Web 不把 `apmq1` 写入 localStorage/sessionStorage、URL、静态产物或前端日志；session signing、query cursor 和 installation HMAC 使用三条独立 key。HTML 使用 restrictive CSP/frame deny/no-referrer，L0-L2 API 和 session 响应都禁止缓存。具体决策与轮换后果见 `docs/adr/0007-同源Web控制台与短时会话.md`。

## 网络与平台安全

- 外部只开放 TLS 1.2+ 的 443；数据库、SigNoz OTLP 和管理面位于私网。
- 反向代理限制 body、连接、header、超时和源速率；应用层再次校验。
- 容器非 root、只读根文件系统、最小 Linux capabilities、固定镜像 digest、SBOM 和漏洞扫描。
- 密钥来自部署平台 secret manager；`.env` 只用于本地示例且不提交真实值。
- PostgreSQL 传输加密、磁盘/备份加密、最小角色；Gateway 无 DDL 权限，迁移使用独立角色。

## 审计与响应

2026-09-12：SQLAlchemy engine 开启 `hide_parameters=True`。应用/Worker 的结构化异常和 Uvicorn/stdlib 异常输出仅保留异常类型与最多 32 个函数/行号，不渲染异常正文、SQL、参数、cause/notes、源码行或局部变量；避免驱动错误绕过 L2 原文读取审计。request ID 和固定事件名继续用于定位。外部日志收集器不得另行启用异常原文或 locals 采集。

审计至少覆盖：密钥创建/轮换/撤销、scope 修改、配置发布/回滚、符号上传/删除、L2 raw 查看、跨租户 break-glass、人工重放、数据导出/删除、管理员查询和保留策略变更。审计记录包含 actor、tenant、动作、对象、purpose/reason、结果、时间、request ID 和来源，不包含 secret 或 raw 字段值。

发现密钥泄漏时：立即撤销、停止对应 scope、查询异常 ingest、生成替换 key、通知应用发布/动态刷新、记录事件复盘。发现跨租户风险时直接阻断发布并假设数据已暴露，启动取证和通知流程。
