# 总体架构

## 运行链路

```text
Android SDK durable outbox
  -> TLS / reverse proxy
  -> Gateway API
       1. request identity + body limits
       2. API key authentication and scope resolution
       3. bounded gzip decompression
       4. protocol decode and whole-batch validation
       5. occurrence normalization + installation HMAC before persistence
       6. transactional inbox insert + duplicate/conflict accounting
       7. durable whole-batch ACK; V2/V3 exact schema/batch/count headers
  -> PostgreSQL inbox
  -> Export worker claim(owner, lease, expiry)
       -> read persisted normalization + field registry projection
       -> OTLP Logs over HTTP Protobuf; registered Metrics remain planned
  -> SigNoz ingester
  -> ClickHouse
  -> SigNoz query / dashboards / alerts

browser -> one-time apmq1 exchange -> short-lived same-origin Web session + CSRF
apmq1/session viewer/investigator -> Query/BFF fixed tenant/app/environment scope
  -> bounded aggregates / event metadata / audited raw access / release decisions

Build CI -> artifact API -> private artifact volume/object store
  -> PostgreSQL symbol artifact index
  -> Symbolizer claim(owner, lease, expiry)
  -> R8 retrace / llvm-symbolizer
  -> release crash inbox row for OTLP export
```

控制面与数据面分离：密钥、应用、配置版本、符号索引和审计属于控制面；事件接收、inbox 和 OTLP 导出属于数据面。控制面故障不得让已经认证且配置已缓存的数据面立即停摆。

## 服务组件

### Gateway API

Gateway 是无状态 HTTP 进程，持久状态只写 PostgreSQL。可横向扩容；负载均衡不要求会话粘滞。它不等待 SigNoz 接收，因此下游故障不会直接阻塞 SDK，但 inbox 容量和积压阈值会触发受控 `503`/`Retry-After`。

### PostgreSQL durable inbox

核心表保存 tenant、eventId、接收元数据、原始规范化 JSON、协议、状态、尝试次数、租约、下次执行时间和错误摘要。`UNIQUE (tenant_id, event_id)` 是最终幂等边界，应用层预查只用于统计，不能代替唯一约束。

批次先完整解码和校验，再开启事务。V2/V3 都校验 schema、SDK、resource、稳定 batch ID、事件数以及请求头/消息体一致性；V3 还要求每事件 occurrence snapshot。Gateway 在写入前用 tenant/domain/key-version 计算 installation HMAC 并删除已知明文。事务内每个新事件插入 inbox，相同内容重放记为 duplicate，不同内容或 occurrence 复用 eventId 返回冲突；只有事务提交后才 ACK。客户端只把 schema、batch ID、event count 三个响应头精确匹配的 2xx 视为成功。数据库不可用、提交状态不确定或请求取消均不返回成功。

### Export worker

Worker 使用 `FOR UPDATE SKIP LOCKED` 认领到期行并设置 owner/lease。网络调用不持有数据库行锁。成功后仅 owner 可完成；失败按指数退避和服务端 `Retry-After` 延迟；超过上限或确定性映射错误进入 dead letter。租约过期后其他 worker 可安全重领。

下游 OTLP 也可能在响应丢失时重复接收，所以导出属性必须保留稳定 `android.apm.event_id`。面向用户的聚合、错误指纹和导出审计以稳定 ID 去重。

### SigNoz

SigNoz 通过官方 Foundry 安装。Gateway 只依赖 OTLP 契约，不连接或写入 SigNoz ClickHouse 内部表。Dashboard/告警资产使用版本化 JSON/API 脚本发布；版本升级失败可回滚到已验证的 Foundry/SigNoz 组合。

### Normalization 与数据质量层

当前 ingest 已在 durable 行上保存 normalization version、exact event family、发生/采集时间、注册字段状态、低基数 indexed attributes、事故指纹和 native identity；OTLP mapper 只导出 allow-listed 属性，Query/BFF 在同一事实层计算首个 Crash/ANR 切片。该初始注册表尚未覆盖所有 SDK 模块，OTLP Metrics、标准 session/device/OS 和可靠事故关联仍未实现：

```text
immutable inbox event
  -> exact module/name registry
  -> trusted/request/event identity classification
  -> occurrence/collection/received time normalization
  -> value availability + raw/aggregated form classification
  -> privacy/cardinality allow-list
  -> LogRecord + optional registered Metric/Span
```

注册表按 schema/module/name/field 版本化；未知字段继续保留在 raw payload，但不会自动成为 SigNoz 可分组属性。任何映射错误只降级对应派生字段，不能丢掉已经 durable ACK 的原始事件。

V2/V3 installation wire 值在完整校验后、durable insert 前替换为 tenant-scoped、domain-separated HMAC 与 key version；已知明文从 payload 删除，OTLP/Query 只看到 HMAC 或聚合值。客户端没有标准 session/device/OS 时，对应能力状态保持 unavailable/unknown，不通过默认值补齐。

身份质量随每条事实持久化，不能只存在于 Dashboard 查询约定：

| `identity_quality` | 来源 | 可用于什么 | 禁止用于什么 |
| --- | --- | --- | --- |
| `AUTHENTICATED` | credential 解析出的 tenant/app/environment | 强隔离、写入和读取 scope | 证明客户端事件内容真实 |
| `OCCURRENCE_BOUND` | 事件产生时写入 durable outbox 的版本/build/installation 快照 | 生产版本对比、安装分母、精确制品匹配 | 越过 authenticated scope |
| `BATCH_DECLARED` | 当前 V2 上传批次 resource | wire 一致性、受控 fixture、兼容查询 | 归因升级前遗留事件的发生版本 |
| `REQUEST_DECLARED` | legacy/request Header | 兼容接收、诊断 | 生产版本比率或精确符号化 |
| `HOST_CONTEXT` | 宿主自定义 context | 经注册后辅助详情 | 作为标准 device/session/build 维度 |
| `ABSENT/INVALID` | 未提供或校验失败 | 显示 exclusion/质量状态 | 填默认值或进入对应分母 |

V3 已把 release/build/installation snapshot 固化进每事件；Gateway 把它标为 `OCCURRENCE_BOUND`。V2/legacy 行继续可查询但保持 `BATCH_DECLARED/REQUEST_DECLARED`，不能通过数据库回填把上传时声明伪装成发生时事实。

### 查询与读取边界

当前 AndroidAPM-Server 已提供首个固定 scope Query/BFF 和同源 Web：`apmq1` 凭据在创建时绑定 tenant/app/environment，浏览器登录只交换一次 raw key，再使用短时 HttpOnly 签名会话；每次请求仍回查 key 的撤销/到期状态。`viewer` 只能读 L0 聚合，`investigator` 才能读 L1/L2、purpose-bound raw 和记录人工发布决策；Cookie 写操作再校验绑定 CSRF，窗口、扫描行数、page limit 与 HMAC 游标均 fail closed。它不是通用 ClickHouse 代理。共享多租户生产仍只能通过这类受控接口或物理隔离 SigNoz，不能依赖用户手动选择 tenant。

Web 产物由独立 Node stage 构建后复制进同一个 Python 镜像，FastAPI 只提供 no-store HTML 和 hashed immutable assets。生产缺 Secure Cookie 或独立 session HMAC key 时配置 fail closed；当前 `apmq1` bootstrap 将来可替换为 OIDC code flow，但 fixed-scope BFF、HttpOnly session 和 L2 审计边界保持不变。

产品查询分成三类：

- 发生事实：按 event time 查询 exact eventId/module/name，用于版本趋势和事故详情。
- 管线健康：按 received/observed time 查询 Gateway/Inbox/OTLP/symbolizer，用于 ACK/可见延迟和积压。
- 质量/分母：按 occurrence release quality、HMAC installation、SDK health、迟到和字段 availability 判断结果是否可计算。

发生时间与接收时间不得混算。`app_exit` 是下一次启动采集的历史退出，发生时间取 `fields.exitTimestamp`；`tombstone_crash` 没有可靠原始时刻时标记 collection-time，不悄悄进入实时发布窗口。

### Symbolization worker

符号制品与遥测 inbox 分表/分存储。当前实现由私有本地/持久卷 adapter 保存制品，PostgreSQL 保存身份索引、SHA-256、大小、任务状态和审计；生产对象存储、KMS 加密和生命周期仍待实现。Java 以 tenant/app/versionCode/appBuild/variant 精确匹配 mapping；Native 再强制匹配 ABI/GNU build-id，不允许按相近版本回退。

启用 symbolizer 且 Crash 元数据完整时，inbox 从 `pending` 转为 `awaiting_symbols`，符号任务使用独立 owner/lease/expiry。成功或最终工具失败后回到 `pending` 进入普通 OTLP 导出；制品缺失时保持 `symbols_missing` 并每 60 秒低频重查，CI 上传精确制品还会立即重新排队。元数据不完整的 Crash 标记 `metadata_missing` 并直接导出 raw；symbolizer 关闭时标记 `disabled` 并直接导出 raw，避免默认配置无限阻塞。

工具命令只接受 JSON argv 数组并使用 `create_subprocess_exec`，不经过 shell。基础镜像不在启动时下载工具；`androidapm-symbolizer` 默认关闭，部署方必须提供固定版本 R8 retrace/llvm-symbolizer、记录版本并挂载私有制品卷。

## 状态机

```text
pending -> processing -> delivered
   ^           |
   |           +-> pending (retryable failure)
   |           +-> dead_letter (permanent/exhausted)
   +-----------+ (expired lease reclaim)
```

Crash 符号化前置状态机：

```text
inbox pending -> awaiting_symbols -----------------------> pending -> OTLP export
                         |                                  ^
symbol job pending -> processing -> symbolized -----------+
                         |        -> failed (exhausted) ----+
                         +------> pending (retryable)
                         +------> symbols_missing --(artifact upload)--> pending
metadata_missing -----------------------------------------> raw export
disabled ------------------------------------------------> raw export
```

禁止从 `delivered` 自动回到 `pending`。人工重放必须生成审计记录并复用同一 eventId，且不得绕过 tenant scope。

## 伸缩与背压

- Gateway 按 CPU/请求并发横向扩容，数据库连接池总量受全局预算限制。
- Worker 按 inbox 到期积压和最老事件年龄扩容。
- 每 tenant 令牌桶限制请求与事件量；全局数据库/积压保护优先于接受更多数据。
- 接近容量水位时先返回带有界 `Retry-After` 的 `429`（tenant 配额）或 `503`（系统过载），不接受后丢弃。
- 大字段、高基数字段和未知字段保留在 raw JSON，但不默认建立 SigNoz 索引属性。

## 数据保留

- 已导出 inbox：默认保留 7 天用于审计/重放，之后分批清理。
- Dead letter：默认 30 天并告警，包含受限错误摘要而非凭据。
- 原始 SigNoz 数据、聚合、符号和审计分别配置保留期。
- 删除请求按 tenant/app/installation/user-scoped anonymous ID 执行，并记录不可篡改审计；备份按既定过期周期自然清除。
