# AndroidAPM-Server 总体规划

> 规划基线：2026-08-28。最初的客户端事实审计基于 `AndroidAPM/develop@e1dd627`，当前实现事实以双仓现有工作树和可执行验证为准；阶段完成仍以自动化及现场验收为准，不以文件、接口或 Dashboard “已经写出”为准。

## 目标与边界

服务端把 AndroidAPM SDK 已经可靠采集的事件变成可租户隔离、可查询、可告警、可符号化的 APM 数据。第一阶段复用 SigNoz 的 OTLP 数据面、ClickHouse、通用查询、Dashboard 和告警能力；本仓库只实现 fixed-scope 发布诊断 Web，不另写通用可观测平台，也不修改 SigNoz 核心源码。

本仓库负责：

- Android 专用 Gateway：兼容现有 Line Protocol、自定义长度前缀 Protobuf，并支持显式 Protobuf V2/V3 envelope、Gzip 和提交后的精确整批 ACK。
- 认证、租户/应用/环境隔离、配额、审计和密钥生命周期。
- PostgreSQL durable inbox、`eventId` 幂等、claim/lease/expiry 和死信。
- Android 事件到 OTLP 的稳定映射和字段注册表。
- Android 专属 SigNoz Dashboard/告警配置。
- 同源 desktop-first 发布诊断 Web、短时 Query 会话和受审计下钻。
- Java mapping、Native symbols、符号化任务和构建制品元数据。
- 版本化远程配置控制面；SDK 拉取、验签、缓存实现仍归客户端。

本仓库不负责：

- 重新实现 ClickHouse、通用时序查询、Dashboard 引擎或告警调度器。
- 端上的采集、落盘、限流、PII 清洗和短期 Token 刷新逻辑。
- 云厂商账号、DNS、证书、短信/邮件供应商和物理设备实验室本身。

## 真实用户与最高频任务

第一阶段的主要用户不是平台管理员，而是需要在发布窗口内做判断的 Android 开发/发布负责人。SRE、质量负责人和安全管理员是重要的协作角色，但不应让管理功能挤占诊断主链路。

| 用户 | 需要完成的任务 | 成功结果 |
| --- | --- | --- |
| Android 开发/发布负责人 | 判断新版本是否引入 Crash、ANR 或性能回归 | 在同一 app/environment 下完成新旧版本对比，看到样本量、数据质量和可下钻事件 |
| 值班开发 | 从告警定位到版本、安装、场景、堆栈和原始事件 | 告警可进入稳定指纹/事件详情；符号缺失、字段缺失和延迟到达有明确状态 |
| SDK/质量负责人 | 判断“没有数据”是健康、未接线、采样、端上丢弃还是服务端链路异常 | 能同时查看 SDK 自健康、Collector/Inbox/OTLP 健康和能力覆盖，未知状态不显示为 0 |
| 平台 SRE | 维持 ingest、inbox、worker、SigNoz 和符号任务 SLO | 可区分客户端问题与服务端积压，并可从 request/event ID 审计完整链路 |

最高频任务按优先级冻结为：

1. 新版本 Crash/ANR 回归发现与阻断判断。
2. 从一个问题聚合下钻到原始证据、符号化状态和受影响安装。
3. 判断数据是否可信，以及问题发生在宿主接线、客户端队列/上传、Gateway/Inbox、OTLP 还是查询资产。

## 产品形态与交付界面

第一阶段是 desktop-first 的内部诊断产品：发布负责人和值班开发在桌面浏览器使用本仓库同源 Web + Query/BFF，并用 SigNoz 验证通用查询/告警资产；平台管理员通过 API/CLI 管理密钥、制品和配置。普通 Android 用户不是服务端界面的用户；本阶段不建设移动端 Dashboard、不在 SDK 中嵌入管理能力，也不另起一套通用前端平台。

单租户/同一信任域 staging 可直接使用 SigNoz UI 验证查询资产。共享多租户生产必须使用本仓库服务端强制 scope 的 Web/Query/BFF 或物理隔离 SigNoz；不能把 tenant filter 交给浏览器。窄屏只保证只读分诊和安全下钻，完整版本对比、长堆栈和管理操作仍以桌面为验收面。

## 产品与数据原则

- **先证明数据可信，再计算健康度。** 每个面板必须展示协议、身份、样本量、延迟和缺失状态；不能把“无事件”直接解释成“零问题”。
- **计数、安装率和会话率分开。** 当前客户端没有生产可用的统一 telemetry session 身份，Crash-free/ANR-free sessions 必须显示“不可计算”；第一阶段只提供事件数、受影响安装数和有数据质量门禁的活跃安装比率。
- **只按真实事件名定义产品事实。** `crash` 模块还包含正常或系统退出的 `app_exit`；不能用 `module=crash` 直接代表 Crash。`app_exit` 与现场 Crash/ANR 可能描述同一事故，未有可靠关联键前不得相加。
- **原始证据不可覆盖。** 规范化、指纹和符号化结果是派生数据；原始 payload、原始堆栈、接收时间和稳定 `eventId` 保留到明确的 retention/dead-letter 策略处置。
- **采集能力与接线状态分离。** Network、SQLite、IPC、WebView、Battery、IO、线程池和 ASM 慢方法依赖宿主接线；服务端在客户端尚未上报 integration evidence 时只能显示 `UNKNOWN`，不能声称未发生或已正确接入。
- **默认关闭高基数扩散。** URL、SQL、路径、堆栈、异常消息、JS 片段和任意 context/extras 只保留在受限详情；进入 SigNoz 可分组属性前必须经过字段注册、归一化、脱敏和基数预算。
- **复用 SigNoz，但不绕过租户边界。** 第一阶段用 SigNoz 的查询/Dashboard/告警引擎；在托管多租户模式落地受控 Query/BFF 或等价隔离前，不能把共享 SigNoz UI 直接暴露给不同租户。

## 场景优先级

| 优先级 | 场景 | 第一阶段交付 | 暂不承诺 |
| --- | --- | --- | --- |
| P0 | 发布版本 Crash/ANR 回归 | 精确事件集、版本/安装分母、指纹、原始详情、数据质量、触发与恢复 | Crash-free session、自动根因结论 |
| P0 | Telemetry 可信度与链路诊断 | `core/sdk_health`、Gateway/Inbox/OTLP/symbolizer 健康、缺失原因分层 | 未上报的宿主接线状态推断 |

| P1 | 内存/GC/线程/IO/SQLite/WebView/IPC | 事件检索、受控字段趋势、异常 finding | 全模块一次性产品化或默认索引所有字段 |

## 首个垂直切片：新版本 Crash/ANR 可信闭环

首个切片冻结为“发布负责人发现新版本 Java Crash/ANR 回归，进入原始事件并判断是否需要止损”。它优先验证一条可真实使用的完整链路，不以铺满所有监控模块为目标。

### 输入与事件口径

- 仅将 `crash/java_crash` 计入现场 Java Crash，将 `anr/anr_detected` 计入现场 ANR。
- `crash/app_exit` 是 API 30+ 下一次启动采集的历史退出证据；只有 `reasonName=CRASH|CRASH_NATIVE|ANR` 才属于异常退出候选，第一版单列核对，不与现场事件相加。
- `native_crash`、`tombstone_crash` 和 `app_exit:CRASH_NATIVE` 在客户端 build identity/module-relative PC 契约完成前只提供原始证据，不宣称精确 Native 符号化。
- 周期性 SDK 健康事件的真实运行时身份是 `core/sdk_health`。`sdk_self_monitor/sdk_health_report` 是当前 helper/test 形态，不是默认周期上报身份。
- V2 `resource.service_version/installation_id` 仍是上传批次级声明，只用于兼容接收和受控 fixture。V3 已把 release/build/installation 作为 occurrence snapshot 固化进 durable event；服务端入库前把 installation 转为 tenant-scoped HMAC。缺失或仅 batch/request-declared 身份的数据参与允许的事件计数，但不进入相应版本/安装比率。

### 用户闭环

```text
发布版本筛选
  -> 数据可信度与样本门禁
  -> 新旧版本事件数 / 受影响安装数 / 活跃安装比率
  -> Crash/ANR 指纹 Top N
  -> 指纹详情与时间趋势
  -> 原始事件、原始堆栈、符号化/字段缺失状态
  -> 发布阻断或继续灰度
  -> 告警恢复与决策审计
```

### 切片退出条件

1. 真实 Android V3 uploader 生成 Java Crash、ANR、`core/sdk_health` 和 `app_exit` fixture，经 Gzip/Gateway/PostgreSQL/OTLP/SigNoz 可查询；V2/legacy 继续做兼容 fixture，重放不产生第二条逻辑事实。
2. tenant/app/environment 来自认证 scope；版本来自每事件 occurrence-bound 快照。installation 只保留 tenant-scoped HMAC 与 key version，原值不进入 durable payload、日志、OTLP 或 Dashboard。
3. 版本对比同时展示事件数、受影响安装数、活跃安装数、identity coverage、SDK drop 和迟到比例；分母不足时不计算百分比。
4. `app_exit` 不被普通退出污染 Crash 数，也不会与 `java_crash`/`anr_detected`重复计为两个事故。
5. 详情保留 raw/symbolized 两套证据；`disabled`、`metadata_missing`、`symbols_missing`、`symbolized`、`failed` 都有用户可理解的状态。
6. 告警 fixture 验证触发、低样本抑制、静默、恢复和重复通知；当前仅按 `module=crash` 的模板不得进入生产路由。
7. 多租户读取路径有服务端强制 scope；若阶段内只部署单租户 SigNoz staging，必须明确标注该限制。

### 剩余跨仓库与现场阻塞

- V3 occurrence、durable codec V4、服务端 HMAC/key-version 和初始 Query/BFF 已实现并通过本地跨仓闭环；但真实应用升级期间的 device fixture、生产密钥轮换和 PostgreSQL/TLS 部署仍需现场验收。
- V3 支持 Native frame identity，但现有真实 Native crash 采集链尚未证明会为每个模块提供 ABI/build-id/module-relative PC；精确 Java/Native 符号化仍需真实 R8/LLVM、制品和 crash fixture。
- 客户端没有统一业务 telemetry session 事件/ID，Crash-free/ANR-free session 指标不可计算。
- `ApmDiagnostics.hostIntegrationSnapshot()` 不自动上传；服务端无法从事件缺失反推 Network/SQLite/IPC/WebView/Battery/IO 是否正确接线。
- 当前有 OTLP Logs、初始 source-reviewed normalization、固定 scope Query/BFF、同源 Web 垂直切片和最小 SigNoz 资产；仍没有 OTLP Metrics、SSO、真实 SigNoz staging、通知路由和 Web 的云端生产验收。

## 技术基线

| 层 | 选择 | 原因 |
| --- | --- | --- |
| Gateway/Worker | Python 3.11、FastAPI、Pydantic | 协议边界清晰、交付与测试速度高；异步 I/O 可横向扩展 |
| 持久化 | PostgreSQL 16+ | 事务唯一约束、`SKIP LOCKED`、可靠租约与成熟运维 |
| 数据交换 | OTLP/HTTP Protobuf | SigNoz 的标准入口，避免绑定 ClickHouse 内部表 |
| 观测平台 | SigNoz `v0.133.0` | 日志、指标、查询、Dashboard、告警一体化 |
| 自托管配置 | SigNoz Foundry `v0.2.13` | 官方当前安装配置来源；本仓库只保存版本锁和覆盖层 |
| 发布诊断 Web | React、TypeScript、Vite | 同源 fixed-scope UI；不把长期 Query key 存入浏览器 |
| 依赖/任务 | `uv`、pytest、Ruff、mypy | 可复现锁文件、静态检查和自动化测试 |

版本号是当前审核基线，不是永久常量。升级必须先跑契约测试、数据映射快照、备份恢复和 Dashboard 冒烟，再修改锁定版本。

## 实施阶段

### M0：规划冻结与仓库基线

- 冻结 v1 ingest API、错误码、限制、legacy 整批 ACK、V2/V3 精确 ACK 和版本演进规则。
- 固化安全模型、数据分类、OTLP 映射、SLO、部署拓扑和 ADR。
- 建立可复现开发环境、检查工具和文档验证。

退出条件：规划文档无所有权矛盾；协议示例可由测试夹具解析；依赖锁可复现。

### M1：可靠 Gateway

- 完成 API key 认证、tenant/app/environment scope。
- 完成 Gzip、Line Protocol、长度前缀 Protobuf、V2/V3 envelope 解码、occurrence 校验、installation 假名化和资源限制。
- 在单个 PostgreSQL 事务中完成整批验证、幂等插入和审计。
- 返回稳定错误体、`Retry-After`、request ID 和整批 ACK。

退出条件：重放、并发重复、ACK 丢失、畸形 Gzip、超限、跨租户伪造测试全部通过。

### M2：OTLP 导出与最小可观测闭环

- Worker 使用租约认领 inbox，导出 OTLP Logs；确定性指标再附加导出 OTLP Metrics。
- 下游超时/5xx 重试，永久错误进入死信；重复 worker 不造成重复事实。
- 提供健康、就绪、Prometheus 指标和运维 API。
- 先交付首个 Crash/ANR 可信闭环和数据质量面板；启动、网络、帧、资源按场景优先级逐步加入，不以面板数量代替验收。

退出条件：从真实 V3 SDK 请求到 SigNoz 可查询形成端到端证据，且 ACK 延迟与可见延迟满足 SLO。当前本地 SQLite 闭环只关闭 wire/query 兼容门禁；在 PostgreSQL/TLS/SigNoz staging、通知触发恢复和读取隔离现场通过前，不能把“新版本回归”产品切片标记为生产完成。

### M3：符号化和远程配置

- 构建流水线上传 `mapping.txt`、Native 未剥离 ELF/符号包、build-id 和校验和。
- Worker 精确按 app/version/build/variant/ABI/build-id 符号化并保存结果/指纹。
- 配置服务签名发布、灰度、过期和 kill switch；客户端只消费有效签名版本。

退出条件：真实混淆 Java 和 Native crash 样本可正确还原；错误 build-id 显式失败；配置回滚与过期回退通过。

### M4：生产部署与发布门禁

- TLS、密钥管理、备份/PITR、容量、保留、灾备、审计和告警齐全。
- 压测、72h soak、故障注入、升级/回滚演练完成。
- 客户端外部制品发布和真机实验结果进入发布门禁。

退出条件：`docs/07-测试与验收.md` 的 P0/P1 条目有可复核证据，所有外部阻塞明确列出。

## 产品 SLO 初始预算

| 指标 | 初始目标 | 说明 |
| --- | --- | --- |
| Gateway 可用性 | 月度 99.9% | 不含明确拒绝的无效/超配额请求 |
| ACK 延迟 | P95 < 300 ms，P99 < 1 s | 32 条/批、区域内、数据库健康时 |
| 查询可见延迟 | P95 < 60 s | durable ACK 到 SigNoz 可查询 |
| 幂等正确性 | 100% | 同 tenant/eventId 不生成第二条逻辑事实 |
| 租户隔离 | 100% | 任何越权读写均为发布阻断 |
| 身份覆盖 | P0 面板展示实际值，不设虚假通过线 | installation/version/session 缺失必须显式；缺失数据不进入对应分母 |
| 数据状态可解释 | 100% 的面板有 empty/error/unavailable 定义 | 真零、无样本、不可计算、字段缺失和链路异常可区分 |
| 恢复点目标 | PostgreSQL RPO ≤ 5 min | 生产需 WAL/PITR；单机开发环境不算 |
| 恢复时间目标 | RTO ≤ 60 min | 以演练计时，不以文档推测计 |

## 完成定义

“服务端完成”必须同时满足：代码、迁移、前后端测试/构建、容器、运维文档、Web、Dashboard/告警资产、真实端到端证据和 GitHub 推送均完成。若 Docker、云主机、DNS、证书、通知渠道或真机不可用，应明确标记为外部待办，不能把本地单测通过写成已经上线。
